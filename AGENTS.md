# Instructions for contributors and coding agents

Read docs/PLAN.md, ONTOLOGY.md, CONTRACTS.md, ACCEPTANCE.md, DECISIONS.md and PRODUCTION_V0.md before coding; Use only the current repository documents. Do not add obsolete plans, archived implementations or copied upstream repositories. Do not change architecture, delete requirements or choose new frameworks without owner approval. Reuse maintained, explicitly licensed components. Never copy unlicensed code from OntoForge. No speculative scaffolding that pretends to be working. Production v0 supports the MCP independently and the Registry, Authority and Workspace mini app surfaces. Keep shared login and OAuth consent separately hosted. Expose approved business tools in custom MCP, never infrastructure management, raw SQL or generic RPC forwarding. Keep Process Kind definitions in Registry; never register a Process execution as an entity. Keep operational tables/API separate, pin the published standard version, and do not implement an execution graph. Never reintroduce old `process` Registry vocabulary.

Work in small vertical slices. Add failing acceptance tests first, implement the smallest complete behavior, run real PostgreSQL and application tests, and report actual results. Use Supabase CLI migrations, generated types and official SDKs. Do not use mock-only security tests as evidence. All tests must fail on broken behavior, no skipped critical gates or manufactured passes. Report exact command, commit/version, test count and evidence; record gaps separately. Follow the role matrix. Never pass browser-supplied actor, role, scope or request-source as identity. Never expose service-role key, token hash, raw secret, privileged SQL helper or unsafe write route. Check membership/credential state on every operation. Use RLS for reads, explicit grants and transactional RPCs for writes, pin search_path on definer routines. Validate dynamic templates/predicates and audit atomically. No direct domain writes outside migrations/test fixtures or trusted mutation path. No production DB reset. Do not run destructive commands against a linked/remote DB.

All changes via feature branches and PRs, linked acceptance IDs and real test output. Independent review required; additional review for auth, RLS, migrations and credentials. No merge with red gates or unresolved review. GitHub access is not needed for independent coding/test work; record branch-protection state accurately. Do not report a milestone accepted without all its criteria. Keep dependencies/lockfiles reproducible and check licenses/security. Do not write secrets into logs, docs, fixtures, commits or exports.
