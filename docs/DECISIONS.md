## Registry and execution boundary

- Process Kind is a registered reusable Center-defined standard, analogous to a skill package. Process is a many-to-one operational instantiation executed by Edges; it is never a Registry entity. Execution graph explicitly deferred until the rest is working.
- Keep a separate Process table. Use immutable versioned standards so executions are reproducible. Exact package format, Edge identity/authorization, status transitions, dispatch, retry and lease policy are proposed implementation details; do not activate them until reviewed and tested.
- Source migrations now use the exact seventeen hosted IDs and SHA-256 hashes. Never replay or rewrite an applied migration; append reviewed forward migrations. Preserve Registry. A fresh installation uses all seventeen on a real Supabase stack.

## Exchange implementation boundary

The current export adapter delivers an authenticated ZIP response rather than the target signed Storage URL. This is an interim implementation, not an approved change to CONTRACTS or ACCEPTANCE. Native Cron scheduling and the end-to-end Storage/Edge verification remain open.

## Prepared execution candidate (not an owner-approved activation)

The private native PGMQ implementation is installed in development and part of the reconciled baseline, without any worker access. Its activation policies remain subject to review. Candidate defaults are owner/admin Center writes, ack-at-claim in the same transaction as a durable fenced attempt, explicit expiration and retry dispatch, same Edge assignment on retry unless a future reviewed reassignment API is added, and 1–3600 second lease bounds. These are implementation candidates, not additional approved architectural decisions. No public execution RPCs, worker identity or scheduler are enabled. The publication Edge adapter is disabled pending approval of the semantic package format and actual Storage integration. No destructive cleanup of uploaded standards on ambiguous publication is performed; orphan reconciliation remains open.

The supplied login UI replaces the earlier identity host UI source. Vercel previews are UI-only by conservative deployment default, with authenticated testing on a stable explicitly configured origin. The private delegated grant candidate is tested but not activated; grant lifecycle, exact tool policies, token audience validation and dispatcher require review.

MCP v6 is active in the designated development Registry. Golden Path first: nineteen tools cover Registry operations, discovery, create-only ontology setup and entity history. The new opt-in `manage` scope requires `write` and current owner/admin role; old credentials are not widened. The actual local acceptance test discovers kinds and schemas and verifies committed data and audit via an independent authenticated API. Broader administrative tools, delegated OAuth, confirmation policy and Vercel deployment remain unfinished. No new architecture or branding.
