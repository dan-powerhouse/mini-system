# Identity provider (working designation only)

The service has no product name, logo, public domain, or brand assignment. The current package contains both login and OAuth consent. The production target hosts them separately and shares login between the mini app surfaces. Supabase Auth remains the issuer and owns users, native credentials, OAuth clients, consent, sessions and refresh tokens. All five Registry kinds are unchanged.

## Implementation

- `apps/identity`: the owner-supplied complete dark login-only Next.js UI, integrated without redesign. Native `@supabase/ssr` 0.12.5 and `@supabase/supabase-js` 2.112.4 are pinned as in the reference. Magic link sign-in is separate from explicit account creation; the pending OAuth authorization ID survives the callback. Passkey use is opt-in and enrollment requires a confirmed non-anonymous account. The OAuth page retrieves issuer-owned request details, shows requested scopes, and uses issuer-returned redirect URLs after explicit approval or denial. The candidate accepts HTTPS and loopback redirects only. No service key is used by the browser or identity host.
- `supabase/migrations/20261124205909_identity_provider.sql`: deployed SQL authorization layer. Restricts existing Registry data and RPCs to direct non-anonymous sessions (or the existing trusted opaque MCP adapter's internal principal). OAuth-issued tokens remain identity-only, including when the user is an owner. Adds a private workspace-scoped account-to-Person link with explicit owner/admin authorization, uniqueness and audited revocation. It does not duplicate native users or create a new Registry kind.
- `supabase/functions/_shared/exchange-http.ts`: the shared human file adapter requires a positive `registry_direct_session` check through the user's JWT before using service-only RPCs. This updated adapter must be activated together with the candidate SQL. Existing hosted import/export/publication functions were not deployed in the prior stage. Do not deploy these updated adapters before the SQL is available.
- `tests/identity/authorization.sql`: transaction-scoped SQL regression candidate (requires native Auth columns, or the extended test shim). `apps/identity/tests`: adapter, continuation and redirect tests.

## Deployment checklist (remaining configuration)

1. **Completed in Registry development:** migration `identity_provider` (hosted version `20261124205909`) installed. Seven identity checks and all 122 earlier SQL/native queue checks passed with simulated JWT claims against managed PostgreSQL 17.12. The live OAuth and OIDC discovery endpoints returned HTTP 200, the JWKS endpoint returned one public key, and there are zero active OAuth clients. OAuth discovery did not advertise dynamic registration. Keep the Registry grant boundary closed to OAuth clients until delegated authorization has been implemented and tested. Do not rerun the migration or reset the project.
2. Choose the stable identity host origin and WebAuthn RP ID. Passkeys are bound to the RP ID. Set the native Supabase Site URL and exact callback allowlist for login. Configure the OAuth authorization URL for the chosen consent origin. Verify session continuation and consent across the two hosts before release. For local development use a matching localhost RP ID and origin on a local Supabase project, not an arbitrary hosted preview. The connector does not expose Auth configuration updates. Keep any existing Auth settings until reviewed.
3. Configure only publishable credentials in `apps/identity/.env.local`. Run `npm ci`, `npm test`, `npm run typecheck`, `npm run build`. Deploy the identity-only UI as an independent Vercel project at the approved stable origin; see `docs/VERCEL.md`. Configure email delivery and enrollment policy in Supabase Auth; no login email delivery was tested here.
4. Register the first OAuth client with exact redirect URIs; use authorization code + PKCE, state and nonce. Verify discovery, issuer, JWKS, ID token, consent approve/deny, refresh and revocation; test real browser passkey enrollment and sign-in on the selected RP origin. Passkeys are experimental in the native SDK.
5. Complete the reviewed delegated Registry access path; the private grant model and check are now implemented and rollback-tested (see `docs/DELEGATED_AUTHORIZATION.md`). Use a distinct grant boundary (client + user + workspace + permitted operations, bounded validity and immediate revocation) before allowing OAuth tokens to call data tools. Native OIDC scopes concern identity claims, not database permissions. The existing nine compatibility MCP tools still use their opaque scoped credentials; OAuth MCP discovery/resource audience validation, delegated grant checks, audit attribution and rate limiting are not yet implemented. Do not accept arbitrary Supabase JWTs as MCP tokens or substitute ID tokens for access tokens. Supabase currently lacks the client_credentials grant; autonomous Agents and Edges retain their separate machine-credential design. No worker is enabled by this module.

## Remaining identity areas identified in the reference and current documentation

- Native OAuth client lifecycle: register/list/update/rotate/revoke clients using Auth administrative APIs; associate a client with an App only after explicit authorization. The reference’s global mandate model is not copied into this workspace-scoped Registry. Do not expose a service key or allow ordinary workspace owners to administer unrelated project-wide clients.
- Account security: manage enrolled passkeys (list/rename/revoke), recovery and native session/consent revocation. Sign-out and initial enrollment exist; account management and recovery tests are incomplete.
- Delegation: enforce per-client/user/workspace and operation grants, audience/resource binding, revocation, and audit before accepting OAuth bearer tokens on MCP or the Data API. No client_credentials grant is available from the native OAuth server. Machine identity remains separate.
- Identity operations: stable RP domain, allowed origins/redirects, Auth consent path, SMTP, enrollment policy, actual authorization code/refresh/revoke and browser passkey tests. Native MFA or additional sign-in methods are optional decisions, not silently enabled. See VALIDATION for the deployment inventory.
